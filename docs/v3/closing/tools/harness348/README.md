# Rebuilt #348 bitwise harness (VIC)

This is a gate tool for V3 wave 1 (the I-1 to I-5 steps). It is **not part of
the wave PR**. chengcli/snapy#348 described a harness that "runs 16 implicit
decks for 10 steps each and compares `hydro_u` byte for byte", but that harness
was never committed. This directory is a rebuild from the description. The
deck details (sizes, initial state, dt, the fixer default with `cell`) are
choices made for this rebuild, not copied from the original.

## What it compares

The harness runs 16 decks, saves `hydro_u` (every variable, ghost cells
included) after each of 10 steps, and compares the bytes of the two
`[10, nvar, nc3, nc2, nc1]` FP64 tensors. Two builds are bitwise equal on the
harness when all 16 decks are identical. `--compare` also prints, for I-3's
rounding target, the largest per-step relative difference of the energy row:
`max |E_B - E_A| / max |E_A|`, taken over the whole array, at each step.

## Decks

There are 2 VIC matrices x 2 gravity-work forms x 4 geometries = 16 decks.
The input YAML files are in `decks/`. They are regenerated by
`h348.py --write-decks decks`; the script's `config()` is the source.

| axis | values |
|---|---|
| VIC matrix | `full` = `implicit-scheme: 9`, `partial` = `implicit-scheme: 1` |
| gravity work | `face` (with `gravity-work-fixer: false`), `cell` (fixer key omitted, so the default is on) |
| geometry | `cartesian` 45 x 8 x 1; `stretched` (`x1rat: 1.05`) 45 x 8 x 1; `spherical-polar` 45 x 1 x 1 at r = 7e7 m; `gnomonic-equiangle` 45 x 4 x 4 at r = 7e7 m |

Every deck uses ideal gas (gamma 1.403461, Rd 3515), the limiter on, weno5 in
both directions, lmars, rk3, reflecting x1 walls and FP64, with no redo
allowed (a redo raises). The initial state is the isothermal hydrostatic
column (T0 786 K, ps 1e7 Pa, g 23.1 m/s^2), with density times
`1 + 1e-3 sin(0.7 i + 1.3 j + 2.1 k)` (`initial_w()`). Each deck takes 10
steps of a fixed `dt = 20 dz / c_s` (304.163 s, a vertical acoustic Courant
number of about 20).

## Running it

You need a snapy build to test, its Python package and kintera >= 2.6.9 on
`PYTHONPATH`, plus torch 2.10. Run each build's own package:

```sh
# reference: main 730b3500 (or any baseline build)
PYTHONPATH=<main-pkg>:<kintera-pkg> python h348.py --device cpu  --out runs/main_cpu
PYTHONPATH=<main-pkg>:<kintera-pkg> python h348.py --device cuda --out runs/main_cuda
# candidate: e.g. the I-1 head
PYTHONPATH=<step-pkg>:<kintera-pkg> python h348.py --device cpu  --out runs/step_cpu
PYTHONPATH=<step-pkg>:<kintera-pkg> python h348.py --device cuda --out runs/step_cuda
# gate: 16/16 identical (exit 0), else exit 1
python h348.py --compare runs/main_cpu  runs/step_cpu
python h348.py --compare runs/main_cuda runs/step_cuda
```

Without a local main build, check a run against the stored checksums instead.
They only match on hardware and builds that give main's exact bits (see below):

```sh
python h348.py --check-manifest runs/step_cpu results/main-730b3500-cpu.json
```

Each run writes `<deck>.pt` (about 11 MB for the set) and `manifest.json`
(sha256 of each dump, shape, finiteness, wall time and torch version).

## Main against main (chengcli/snapy 730b35007d16389c64116e4bf9d2fe93707e29e9)

Builds: Release, per the README (`-DNETCDF=ON -DBUILD_TESTS=ON`), torch
2.10.0+cu128, kintera v2.6.9 (b8e726ce), gcc 13.3, nvcc 12.9. The GPU is an
RTX 5090 (sm_120). The CPU build and the CUDA build were separate.

| comparison | identical | note |
|---|---:|---|
| CPU build, CPU: run a vs run b | 16/16 | 16 dumps pairwise distinct |
| CUDA build, CUDA: run a vs run b | 16/16 | 16 dumps pairwise distinct |
| CUDA build on CPU vs CPU build | 16/16 | |
| CUDA vs CPU (information only) | 0/16 | worst energy-row rel 3.4e-15 |

Wall time for the 16 decks (in-script, after import): CPU 0.91-0.92 s and
CUDA 2.25-2.32 s on an idle machine. Under full machine load, a whole CPU
process took 3.2-4.1 s, import included.

The checksums are in `results/`. They come from this machine. Another
CPU (other SIMD paths) or GPU may give other bits for main itself, so always
pair a step run with a main run on the same machine.
